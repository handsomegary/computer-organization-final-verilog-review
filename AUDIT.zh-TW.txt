方法：逐檔靜態檢查、module 相依與接腳檢查、頂層編譯及獨立 assertion 測試。

一、指定簡報的需求

第 2 頁：Verilog MIPS，十種指令 lw、sw、add、addi、sub、and、or、slt、beq、jump。
Level A 為 single cycle、B 為 pipeline、C 為 hazard detection。簡報沒有說
全部 level 都必須完成，也沒有列評分權重，以下分別評估其聲稱的架構與功能。

第 3–4 頁：設計一個或數個程式，轉為機器碼放入 instruction memory。
第 5 頁圖包含 PC+4、branch immediate << 2 與 jump address 的組合路徑。
第 7 頁圖包含 forwarding、load-use hazard detection、PC/IF-ID stall 與 bubble。
第 8 頁的相依程式：
    sub $2,$1,$3
    and $12,$2,$5
    or  $13,$6,$2
    add $14,$2,$2
    sw  $15,100($2)
此程式沒有 lw，故另外測試 load-use；sw 在此主要測試 base register 相依。

第 9 頁另要求 RTL、top-module testbench、含架構與模擬的 PDF。
本次依使用者指示只擷取 Verilog，不對已排除的原有 PDF 做完整繳交包評分。

判讀限制：第 4 頁使用非標準暫存器別名，且 +40/+400 註記不一致，因此沒有
單憑別名編號判不合格。signed slt 回傳 0/1、addi 不寫 memory 等採用 MIPS
指令語意作為功能檢查。未聲稱符合完整 MIPS32 規格、例外或溢位機制。
圖未明訂 branch delay-slot 政策，分支測試採一般教學 datapath 的無 delay-slot
語意；若版本要求以 NOP 排程，須自行說明，不能據此宣稱完整自動 hazard 處理。

三、驗證如何解讀

既有 testbench 多只產生 clock/reset，沒有 assertion；能執行或產生波形
無法證明指令結果。verification/ 的新測試會比較預期暫存器／memory 值，
失敗時使用 $fatal；附有普通算術等通過基準，避免只看見失敗卻不知是否正確驅動。

部分整合測試在 testbench 內透過 hierarchy 初始化 ROM、register、memory，
以隔離特定指令與相依性。這只建立測試情境，未改動保存的 RTL 或原有程式。
未做 FPGA synthesis、timing closure 或完整形式驗證。

reports/ 另保存所有實際 return code、工具診斷與 assertion 結果。
若有編譯器／環境異常，與原始碼的語法錯誤及 assertion 失敗分開記錄，
不把工具異常當成 Verilog 不符合的理由。

最終使用官方 Windows 套件 Icarus Verilog 12.0 (devel)，版本識別
s20150603-1539-g2693dd32b，完成 38 個案例。最終執行沒有工具 crash 或 timeout。
33 個案例正常完成 elaboration；5 個案例有編譯錯誤，對應 01 重複模組、
03 hazard 的接腳寬度、04 named-port 錯誤三類問題，其中 03 重複出現於
原始頂層及兩個無法進行的整合測試。
27 個實際執行的 assertion 測試：10 通過、17 失敗。
另有 4 個原始 testbench 只作 smoke run，不計入功能通過數。
33 個成功 elaboration 的 compiler return code 均為 0。
